# Job Profiles and Applications

Review job-platform profiles and recommendations for the configured target roles and adjacent technology senior roles; create truthful general or tailored CVs and prepare supported profile/application fields for user review. This bundle has no application ledger, so do not submit applications until a separate, tested ledger is deployed. Never infer biography from a job ad or invent experience, metrics, credentials, dates, or work authorization.

This is an employment-only workflow. Use it only in the standalone jobsearch-assistant `job-agent` deployment; do not access, summarize, or store health-assistant data. If a health-related question arrives, do not load this skill or answer from its files; direct the user to the separate health assistant.

## When to Use

- The user asks to review or complete a job-platform profile (LinkedIn, or another ATS), screen suggested jobs, prepare CV/cover letters, or apply.
- Do not use for unsolicited applications to roles outside the agreed criteria.

## Prerequisites

- Obtain a canonical CV in DOCX, Markdown, or PDF, plus optional profile/portfolio links, job preferences, authorized contact details, and explicit submission boundaries. The importer accepts DOCX, Markdown/text, and selectable-text PDF and records source paragraph, line, or page/line locations. An image-only PDF requires local OCR followed by user review; never treat unreviewed OCR as verified fact. Parse into `profile.json` and have the user resolve ambiguity before application.
- Before job discovery, read the YAML file at `$JOB_SEARCH_PREFERENCES_FILE`. Use its `role_families` and `locations` as defaults when the user has not supplied criteria for the current task. Explicit current-task criteria take precedence; an empty list means ask the user rather than infer a value. These preferences are not authorization to submit applications.
- For a browser use Hermes `browser_exec`; use `browser_vault` only when a credential is already stored in the job profile's own vault. Never request or enter a password or one-time code through Telegram. Stop at CAPTCHA, security checks, legal attestations, inaccessible pages, or unsupported forms. The browser is remote with its own profile/session; a login on the user's laptop is not shared with the job agent.
- In the standalone `jobsearch-assistant` `job-agent` Compose service, keep CVs, profile JSON, and drafts under `/opt/data/job-applications`; use `$JOB_DOCS_PYTHON` and `$JOB_DOCS_SCRIPT` for the document pipeline. Never place employment data in the health-agent home, health `private/documents`, or this skill directory. Use a fresh revision directory for each generated package; the builder refuses overwrites.

## Profile review

1. Open the signed-in profile and read the headline, About, Open to Work details, Experience, Education, and visible skills. On LinkedIn's scrollable layout, scrolling `window` may not load sections: identify the actual scrolling `main`, scroll it in stages, and wait for lazy-loaded sections. Open the full Experience and Skills detail pages before concluding a recent role or skill is absent.
2. Compare the complete profile with the current source CV and the user's target roles. Prioritize material discrepancies: a missing current role or unexplained date gap, a consulting-only headline/About when pursuing full-time roles, missing evidence for recent specialized work, and Open to Work title/location settings that hide relevant jobs. Check whether top skills communicate the target specialization rather than merely listing generic legacy skills. Do not invent accomplishments or claim expertise the CV does not support.
3. Recommend only changes likely to affect recruiter understanding or discovery; explicitly say the profile is good as-is if none matter. Give the specific field, observed mismatch, and concise proposed fix. Keep older credible history intact rather than rewriting for cosmetic reasons. Open to Work location settings may not express conditional geography (broad hybrid but restricted onsite), so explain the tradeoff and continue manual screening. Do not edit the profile unless the user asks.

## Reusable ATS profile and generic CV

1. Open the signed-in platform's actual profile editor and inspect the fields and existing values before writing. Build a reusable, source-grounded CV from the canonical profile, rather than reusing one employer-tailored package. The existing document builder can make a general CV with a neutral job descriptor, default role-fact order, `include_cover_letter: false`, and a private copy of verified contact details; keep the original canonical source and earlier submitted files intact. Version the output when a correction arrives, run text/fact tests, rasterize every PDF page, and inspect layout before upload.
2. Upload through the site's ordinary resume control and wait for parsing; inspect what was autofilled before supplementing it. Enter a concise bio, recent employment, education, skills, contact links and work preferences only from verified source facts. If a structured role or degree requires an exact month that the source lacks, ask the user or leave that entry incomplete rather than picking a plausible month; the full CV can still carry year-only dates. Record a newly confirmed month in the canonical source with provenance, rebuild a new generic CV version, replace the uploaded file and confirm parsing did not overwrite accurate fields.
3. Treat preference controls as discovery filters, not a substitute for conditional screening. Ask for the user's current target country, region, commute radius, and on-site/hybrid/remote conditions each time they are not supplied; do not infer location from an old profile, machine, or previous session. Leave unsupported salary, relocation, fluency and voluntary self-identification blank. Reload the profile and read back each saved section; report the site's actual completion checklist separately from visible populated fields. Keep the uploaded filename, exact file fingerprint and profile URL in the job-only work record. See `references/browser-application-forms.md` for supported form controls and cross-host upload limitations.

## Application procedure

1. **Criteria.** Confirm role families, seniority, target country/regions for hybrid (a label alone is insufficient; inspect actual office/attendance requirements), fully remote policy, and any on-site city restriction. Use configured role/location defaults only when the user has not supplied current-task criteria; never silently add or substitute locations. Confirm relocation, salary, language, work authorization, dealbreakers, and submission policy.
2. **Discovery.** Start from the signed-in search or recommendation page the user names; preserve its location and filters rather than silently switching platforms. Search several role-family phrases, collect each batch into workspace JSON, then deduplicate/count URLs or IDs programmatically. Read promising full postings; compare title with actual duties, seniority, hard skill requirements, office city and attendance cadence, because badges such as `Hybrid` or `Remote` can obscure a three-day office requirement or local customer pod. When the user flags a missed role by company name, search spelling variants and current posting IDs, inspect the signed-in full posting, and distinguish a recruiting agency from the actual employer; reposts can describe the same venture with different funding-stage details. Record URL, employer, recruiter if distinct, location, work model, posting evidence, date seen and state; distinguish newly surfaced from newly posted. When asked for an unapplied queue, use only a real configured job ledger and dated discovery files; absence from a missing ledger is not proof that the user has never applied. Cross-check the ledger before recommending or submitting, and separate shortlisted review from approved applications. On LinkedIn, cards are `[role=button][componentkey^=job-card-component-ref-]` and page controls are `button[aria-label="Page N"]`; wait for the active page marker before appending. Report observed search scope rather than claiming an exhaustive market search. Never use scraping bypasses or bulk automation against a login wall.
3. **Qualification and form preflight.** Compare required qualifications against source facts, then open the live employer form *before* investing in tailored documents: its screening questions can expose a disqualifying hard requirement that the listing summary obscures. Inspect all required fields and radio questions without uploading or submitting. Reject role/location/model mismatch and uncertain hybrid office locations pending clarification. If a hard-skill Yes/No question is not source-supported, leave it unanswered, ask the user for concrete project/deployment evidence (or an explicit No), and mark the package draft-only; never turn adjacent cloud experience into production expertise on another cloud. Disclose gaps and conflicting requirements, and rank on actual responsibilities, scope and experience rather than title alone.
4. **Documents.** Import DOCX, Markdown/text, or selectable-text PDF with `"$JOB_DOCS_PYTHON" "$JOB_DOCS_SCRIPT" import-source --source SOURCE --out "$JOB_APPLICATION_HOME/profile.json"`; source hashes and paragraph/line/page locators are retained. Review every extracted section against the original and resolve ambiguity with the user. Image-only PDFs require OCR followed by user review. Create per-job `job.json` and `selection.json` with validated fact IDs. Build each package into a fresh revision directory under `$JOB_APPLICATION_HOME/drafts/<job-id>/<revision>`; the builder refuses overwrites. Produce a cover letter only when useful, then read it and visually inspect each PDF page.
5. **Apply.** This bundle has no tested application ledger, so prepare drafts and stop before submission. Do not click Submit or claim an application was sent. Never infer legal, salary, relocation, or work-authorization answers. Stop at ambiguity, CAPTCHA, security checks, legal attestations, or unsupported forms; never bypass platform safeguards. Live submissions stay disabled until a separate ledger records per-job approval, document hashes, form answers, and destination confirmation.
6. **Verify and notify.** Read back the exact submitted target: application success/confirmation, status under My Jobs/Applied, or employer confirmation email. Some ATS forms request emailed human-verification **after** the first submit click; leave the application blocked/pending until the user completes the code and a confirmation appears. Log timestamp, job ID/URL, documents, answers, confirmation and any uncertainty; notify the user with the outcome and blockers, not simply that a button was clicked. If proof is absent, report `unverified`, never `applied`. If the user elects to skip a legally attested form, record `skipped` rather than leaving it `blocked`.

## Recurring job scouting

Recurring scouting is not configured by this repository: there is no `tracker.py` or application-ledger schema here. Do not claim cross-session duplicate checks, persistent application history, or schedule daily scouting until a separately reviewed ledger is installed under `$JOB_APPLICATION_HOME` and tested. If configured later, use its actual documented commands; never invent a `tracker.py` interface. Any scheduled task still requires explicit user authorization and must not auto-apply.

## Data contract

`profile.json`: importer output has `source` (absolute path, SHA-256, format), `provenance` (paragraph/line/page locators), `name`, `headline`, `contact` (only present values), `profile_summary`, `highlights`, `core_expertise`, `technology`, `facts`, `roles`, `earlier_experience`, `education`, and `skills`. DOCX keeps paragraph indexes, Markdown/text uses line numbers, and PDF uses page/line locators. Do not infer missing contact fields. Every claim and credential must come from the user's verified source.

`job.json`: `{ "id":"...", "title":"...", "company":"...", "url":"...", "location":"...", "work_model":"..." }`.

`selection.json`: `{ "role_fact_ids":{"0":["r1_1"]}, "include_cover_letter":true, "cover_fact_ids":["h1","r2_1"] }`. `role_fact_ids` is a priority ordering, not an exclusion filter: unselected role bullets remain in the CV. `cover_fact_ids` (up to four IDs from source `facts` or `highlights`) selects job-relevant, source-grounded evidence for the letter; unknown IDs fail. The letter never asserts unverified fit. Edit only user-approved source facts, never the generated PDF directly.

## Pitfalls

- Suggested jobs may be stale or promoted; an Easy Apply button is not confirmation that an application was sent. This bundle has no persistent ledger, so absence from its files is not proof the user has never applied. Do not claim a submission or cross-session duplicate check.
- The job-agent browser has its own session and vault; it does not inherit laptop cookies. CDP file paths resolve on the browser host, and a click or upload event is not a submission confirmation. Verify the job profile's own account session for each task.
- On a remote VPS browser, saving the LinkedIn login in the VPS vault permits password fill but does not share the user's laptop cookies. LinkedIn may trigger a CAPTCHA/security checkpoint after sign-in; stop and report it, do not bypass or claim authentication. Completing a challenge in the Mac browser does not automatically authenticate the isolated VPS browser.
- Build one restrained ATS-safe CV content model for DOCX/PDF: a single column, clear name/headline/contact hierarchy, understated section dividers, bold role lines, and consistent indented bullets. Text round-trip alone misses clipping, orphan headings, missing glyphs, and page-break defects: rasterize and inspect every PDF page after style changes, especially the first experience block, and rerun fact tests. Keep roles together across page breaks. Do not claim DOCX visual fidelity without an office renderer; check RTL layout separately.
- An image-only PDF is not parsed; OCR it locally, then review and correct the extracted text against the source before importing it. PDFs with selectable text can still have broken reading order, so inspect the parsed sections and source locators before relying on them.
- The importer recognizes common section aliases and fails on unknown headings or incomplete role facts rather than silently dropping content. Contact email is optional for drafting, not authorization to submit a form with an invented email. Generated drafts contain private contact data; keep them in the isolated job-agent volume.
- When adding a LinkedIn Experience entry, month can be left blank if only its start year is known. Turn off the default “I currently work here” for ended roles, and choose the *existing headline* radio option before saving: LinkedIn otherwise defaults to replacing the headline with the new job title. Read back dates, employer, and headline after saving.
- Open-to-work controls may not express conditional geography. Use only user-approved locations and manually screen each role's actual office/attendance requirements. Reopen details after saving to verify.
- On the Skills detail page, Resources → Reorder exposes keyboard-accessible sortable handles. Focus a handle, press Space, use ArrowUp/ArrowDown, then Space to drop; reload to verify. A newly added skill may appear first automatically. Do not attach independent project skills to an employer without evidence.
- User corrections to employment dates/name must also update the restricted canonical profile JSON with correction provenance, so future CVs do not resurrect stale “Present” wording. Do not rewrite the original CV or historical submitted artifacts; rebuild and inspect a fresh sample from the corrected profile.
- Some jobs redirect to external ATS requiring an account or complex questionnaires. Pause for missing answers; report blockers rather than guessing.
- Rippling résumé parsing can infer a *current* company from the most recent (ended) role and prefill a country code separately from an international phone number. Clear the false current company, avoid duplicating the phone prefix, and select a genuine location-autocomplete option. A generic “Unable to apply; try again later” can precede a successful retry: retry at most once when the form explicitly allows it, then require the confirmation screen before recording submission.
- Comeet/Spark Hire Angular fields may discard `fill_input` typing; focus the actual field and use CDP `Input.insertText` if needed, then check DOM validity and values. Upload success is not submission; wait past the submitting state for its thank-you receipt.
- Glassdoor.de currently lists German jobs, but its results may be noisy, promoted, stale, or link to external ATS sites. Treat it as an optional secondary discovery source: verify the live employer posting and current terms on the destination site. Do not assume a Glassdoor Recruiter profile, onboarding flow, visibility default, legal terms, salary units, or location behavior; inspect the actual page and get consent before making a profile visible or accepting new terms. A missing or stale employer application route is not an open role or a submission confirmation.
- This workflow is not a scheduled monitor until cadence, delivery destination and authorization are agreed and the job is explicitly scheduled.

## Verification

- Every generated claim maps to the user-approved `profile.json` source; every selected ID resolves within its role.
- Both output formats pass extraction checks and visual review; cover letter produced only when needed. Run `scripts/test_application_docs.py` with the venv Python for the synthetic positive and negative cases before the first live application.
- No application ledger ships in this bundle. Until a tested ledger is installed under `/opt/data/job-applications`, do not claim cross-session duplicate checks or durable application status and do not submit. Before enabling applications, implement approval records, immutable events, document hashes, destination confirmation, and duplicate detection.
